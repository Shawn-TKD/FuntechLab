# 连接保持与界面重建（v12）

> 这篇记录一个**极其隐蔽、但影响全局**的问题：
> 「刚连上的相机会莫名其妙变回未连接」「重连报 `camera connect failed -214`」
> 「日志里凭空出现『已取消上传』」。
>
> 根因不是相机、不是 SDK、不是 WiFi，而是 **Activity 生命周期**。

## 1. 现象（真机，小米 MIX Flip）

App 启动后日志区长这样（**同一进程 pid 11607，2 分钟内 4 次重复**）：

```
15:37:08 I HeartbeatUI: SDK 已初始化，权限已就绪。
15:38:23 I HeartbeatUI: 已取消上传（已下载的文件仍留在缓存里…）      ← 用户根本没点过上传
15:38:23 I HeartbeatUI: 已取消上传（已下载的文件仍留在缓存里…）
15:38:23 I HeartbeatUI: SDK 已初始化，权限已就绪。                  ← Activity 又重建了
15:38:49 I HeartbeatUI: 已取消上传（…）
15:38:49 I HeartbeatUI: 已取消上传（…）
15:38:49 I HeartbeatUI: SDK 已初始化，权限已就绪。
…
15:39:02 I HeartbeatUI: 点击连接 GO Ultra
15:39:07 I HeartbeatUI: ❌ GO Ultra 连接失败：camera connect failed -214   ← 会话被上一次占着
15:40:15 I HeartbeatUI: 点击连接 GO Ultra
15:40:16 I HeartbeatUI: ✅ 相机已连接（WiFi 直连）
```

随后 `netstat` 显示**与相机的连接正在被拆除**：

```
tcp  192.168.42.4:58248 -> 192.168.42.1:80  FIN_WAIT1
```

而界面顶部始终写着「相机: 未连接」——**明明刚连上**。

## 2. 根因

三个问题叠在一起：

### 2.1 主因：`onDestroy` 把整条链路拆了

```kotlin
// 旧代码（错的）
override fun onDestroy() {
    super.onDestroy()
    if (::orchestrator.isInitialized) runCatching { orchestrator.cleanup() }
}
```

`cleanup()` → `disconnectCamera()` → `camera.release()` + `monitor.close()` + `simulated.stop()` + `scanner.stop()`，
外加 `uploader.release()`。

而 `HeartbeatOrchestrator` 是在 `onCreate` 里 `new` 的：

```kotlin
// 旧代码（错的）
orchestrator = HeartbeatOrchestrator(this)
```

于是**任何一次 Activity 重建 = 整条链路推倒重来**。折叠屏上触发重建的动作多到离谱：
折叠/展开、旋转、深色模式切换、字体缩放、多窗口…

### 2.2 次要因：「已取消上传」是噪音

`ClipUploadManager.release()` 内部调了 `cancel()`，而 `cancel()` 又**无条件**打日志。
所以每重建一次，日志区就多两条「已取消上传」——
排查时被它误导过，以为是用户点了取消。

### 2.3 假象放大器：重建后 UI 是新的，状态是旧的

编排者（假设活着）连着相机，但新 Activity 的界面全是布局默认值 →
显示「相机: 未连接」→ 用户以为掉了 → 反复点重连 → 撞上 `-214`（相机会话是独占的）。

## 3. 修法

### ① 编排者改为**进程级单例**

```kotlin
companion object {
    @Volatile private var instance: HeartbeatOrchestrator? = null
    fun get(context: Context): HeartbeatOrchestrator =
        instance ?: synchronized(this) {
            instance ?: HeartbeatOrchestrator(context.applicationContext).also { instance = it }
        }
}
```

要点：
- 内部一律用 `applicationContext`（编排者活得比 Activity 久，握 Activity context 就是泄漏）；
- 对外不再提供「随便 new」的入口。

### ② Activity 只**挂/摘** UI 回调，按 `isFinishing` 区分意图

```kotlin
override fun onDestroy() {
    super.onDestroy()
    if (!::orchestrator.isInitialized) return
    runCatching {
        if (isFinishing) {
            orchestrator.cleanup()      // 真的退出了 → 释放相机与 GATT
        } else {
            orchestrator.detachUi()     // 只是配置变更 → 只摘回调，连接原样留着
        }
    }
}
```

- `detachUi()`：`callback = null` + `uploader.setListener(null)`，**不动任何连接**。
  （必须摘，否则单例一直握着 Activity 的匿名内部类 → 每次折叠泄漏一整棵 View 树。）
- `cleanup()`：仅在用户真正退出时调用。

### ③ 重建后**回填真实状态**

新增 `HeartbeatOrchestrator.snapshotForUi()`：

```kotlin
data class UiSnapshot(
    val cameraConnected: Boolean,
    val captureArmed: Boolean,        // 「会话开着」而不是「相机此刻在录」（间隔模式两者不同）
    val heartRateDeviceName: String?,
    val simulating: Boolean,
    val uploadBusy: Boolean,
)
```

`MainActivity.setupOrchestrator()` 里第一件事就是：

```kotlin
restoreStateFromOrchestrator()   // 把单例里已存在的状态画到新界面
```

回填后日志会明确写一行，避免用户误解：

```
↻ 界面重建，已恢复既有状态：相机、心率设备（无需重连）
```

为此给下层补了三个只读状态口：
`CameraController.isArmed()`、`HeartRateMonitor.isConnected()/currentDeviceName()`、
`SimulatedHeartRateSource.isRunning()`。

### ④ `configChanges` 减少无谓重建

```xml
<activity
    android:name=".ui.MainActivity"
    android:configChanges="orientation|screenSize|screenLayout|smallestScreenSize|keyboardHidden|density|uiMode|fontScale|navigation"
    ... />
```

这只是「少重建几次」的优化；**真正的正确性来自 ①②③**——
即使 Activity 还是被重建（进程被回收、其他配置变更），链路也不会再被拆掉。

### ⑤ 顺手把机型和文案解耦

界面原来写死「连接 GO Ultra」，而实测连的是 **GO 3S**。
现在连接成功后从 SDK 探一次真实机型：

```kotlin
cameraModelName = camera.system.fetchCameraType().getOrNull()?.getOrNull()?.displayName
// → "✅ 已连接 Insta360 GO 3S（WiFi 直连）"
```

> GO Ultra 与 GO 3S 走的是同一套 SDK、同一套接口，控制逻辑完全一致，
> 所以**代码里没有任何「按机型分支」**——参数能力一律运行时问相机
> （见 `probeLapseTime()`）。这里只是「别在界面上撒谎」。

## 4. 顺带修掉的两个坑

| 坑 | 症状 | 修法 |
|---|---|---|
| **测试服务只监听 IPv4** | 手机经 `adb reverse` 连上了、却收到 **0 字节**响应 | `upload_server.py` 支持 `--host ::` 双栈（关 `IPV6_V6ONLY`），因为 Windows 上 adb 往 `localhost` 转发常优先走 `::1` |
| **adb 守护进程被回收** | `adb reverse --list` 变空，转发莫名其妙失效 | 用 `adb -L tcp:5037 nodaemon server` 常驻（普通 `adb start-server` 会在宿主命令结束后被回收） |

## 5. 复测要点

1. 连上相机 → 把手机**折叠再展开**（或旋转）。
   - ✅ 期望：界面顶部**仍显示「相机: 已连接」**，日志出现「↻ 界面重建，已恢复既有状态：相机」；
   - ❌ 修复前：变「未连接」，且日志刷出「已取消上传」。
2. 再点一次「连接相机」不应报 `-214`（因为会话没被拆，也不需要重连）。
3. 点「停止/断开」或按返回键退出 → 日志出现「Activity 结束（isFinishing）→ 释放相机与心率连接」，
   这时才真正断开。

## 6. 给同类 App 的通用教训

> **「长连接」不能挂在 Activity 上。**
>
> 判断标准很简单：这个资源需要「跨界面重建」活着吗？
> 需要（BLE、相机 SDK 会话、前台服务、下载任务）→ 放 Application 级单例，
> Activity 只挂回调，并在 `onDestroy` 里**按 `isFinishing` 分流**：
> 真退出才销毁，配置变更只解绑。
