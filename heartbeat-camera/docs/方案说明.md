# 心跳触发相机 · 方案说明

> 完整背景与分步操作见同目录 `README.md`。本文凝练"为什么这么做"与"以后能改什么"。

---

## 1. 目标

心率超阈值自动让 GO Ultra 开拍（**录像 / 间隔拍照可选**），回落后自动停。
可作为黑客松"双世界"demo 的实时采集触发插件。

## 2. 你是谁、你有哪些硬件（2026-09 状态）

| 硬件 | 角色 | 说明 |
|---|---|---|
| **Garmin FR255** | 真心率源 ✅ | 支持标准 BLE 心率广播 `0x180D/0x2A37`，安卓手机直接订阅，**零写表程序** |
| **Insta360 GO Ultra** | 被控相机 ✅ | 复用已下载的 Insta360 Android SDK 2.1.5 控制 |
| 华为 Watch Fit 4 | 已被放权 | 跑 HarmonyOS 5，但手机侧读实时心率被华为权限墙卡（`HEALTH_SENSOR` 仅限研究机构），个人开发者走不通 → 仅作 UI 人工看心率佐证 |
| RDK X5 | 可选模拟 | 无心率传感器；如有精力可写"模拟 0x180D 广播"当离线 HR 源，但非必需 |
| 心率传感器模块(胸带/MAX30102) | 无 | 不依赖。Garmin 已是真值 |

## 3. 三条路线的取舍（为什么落在这个方案）

| 路线 | 实时性 | 落地难度 | 结论 |
|---|---|---|---|
| A. 华为 Fit 4 手表 App → 发手机 | 秒级 | 高：华为开发者账号+DevEco+华为调试手机+Wear Engine 权限 | ✗ 30h 内风险高 |
| B. 标准 BLE 心率胸带 | 秒级 | 低 | 无硬件，弃 |
| C. **Garmin FR255 标准 BLE 广播** | 秒级 | **低** | ✅ **采用** |
| 模拟心率（本工程自带） | 1Hz | 零 | ✅ 离线/开发/演示兜底 |

> 结论：**Garmin FR255（真值）+ 模拟心率（兜底）双源，共用同一套安卓接收端**。华为 Fit 4 不再作为 30h 演示依赖。

## 4. 阈值逻辑（防抖关键）

```
state = PAUSED
心率 ≥ on  → 开始拍摄，state = REC     （默认 on=110）
心率 <  off → 停止拍摄，state = PAUSED （默认 off=100，回差 10 拍）
区间内保持不变
```

回差防止心率在阈值附近抖动导致相机疯狂开关。

**阈值现在可在 App 上改**（`AppSettings` 持久化到 SharedPreferences），因此：

- `ThresholdEngine` 的阈值改为**可变属性**，并在 setter 里维护不变量 `offThreshold < onThreshold`。
- 用户若把停止阈值填得 ≥ 开拍阈值，`AppSettings.save()` 会自动把它压成 `on − 1`（迟滞失效比"按用户字面值执行"危害更大）。
- 改设置后会 `engine.reset()`，避免"新的开拍阈值已低于当前心率、但状态还停在 PAUSED"导致不触发。

## 4·5 拍摄模式（录像 / 间隔拍照）

| 模式 | FunctionMode | 参数 | 行为 |
|---|---|---|---|
| 录像 | `VIDEO_NORMAL` | — | 超阈值开录，一直录到回落 |
| 间隔拍照 | `PHOTO_INTERVAL` | `lapse_time` | 超阈值后每 N 秒拍一张，回落停止 |

**关键决策：间隔拍照交给相机固件，不在手机侧跑定时器。**

依据：GO Ultra 固件配置 `assets/insta/json/params/go_ultra.json` 实证存在 `PHOTO_INTERVAL` 模式与
`lapse_time` 参数，合法值 `[0, 1, 3, 5, 10, 30, 60, 120]` 秒。

为什么不用软件定时器反复 `startCapture()`：BLE/WiFi 往返有延迟，间隔会不准；且每次往返都唤醒通信链路，
耗电明显高于让固件自己按节拍拍。**一次 `startCapture()`，相机自己拍到 `stopCapture()`。**

⚠️ `lapse_time` 只接受上面那组离散值，用户填 7 秒会被相机拒绝或静默忽略。
因此 `CameraController.applyInterval()` 用 `getSupported()` 拿**相机自己报上来的合法值**（不硬编码，
换 X4/X5 也能自适应），把用户输入**吸附到"最接近且不超过"的合法值**并提示实际生效值。

⚠️ 参数列表是**模式相关**的：`lapse_time` 只有在切到 `PHOTO_INTERVAL` 之后才出现在 `getSupportParam()` 里。
所以顺序必须是「先 `functionMode.setValue(...)`，再 `applyInterval(...)`，最后 `startCapture()`」。

## 5. 工程关键决策（相对官方 demo 做了哪些简化）

- **连接只走 WiFi 直连**（`CameraDevice.get(WIFI).connect(wlan0)`）：
  - demo 已证实纯 BLE 连上后不能预览/看相册；`capture.startCapture()` 能否纯 BLE 下发未实测。
  - 为"当场能演"优先，用最稳的 WiFi 直连。BLE 引导切 WiFi 那条可作为进阶优化。
- **Maven 凭据不硬编码**：官方 demo 把 `insta360guest/密码` 写死在 settings.gradle.kts。本工程改为从 `~/.gradle/gradle.properties` 读，避免撞"代码原创、无版权争议"底线（交 clean repo 必须）。
- **只依赖 sdk-camera，不依赖 sdk-media**：`sdk-media` 会传递引入 `bmgmedia`（`libarvbmg.so` 135MB 等约 155MB 原生库），
  而本工程只做实时触发拍摄、不做相机文件下载/剪辑。去掉后 APK 从 ~190MB 降到 ~35MB。
- **参数在 App 上可调且持久化**：阈值/间隔/模式存 SharedPreferences，冷启动恢复；
  这些原本写死在代码里，演示时改一次要重新打包，不可接受。

## 6. 风险 / 待验证

- [ ] **capture 是否必须 WiFi**：`startCapture()` 能否纯 BLE 下发未实测。当前依赖 WiFi 直连，若现场不方便切热点，需验证 BLE 下发。
- [ ] **间隔拍照真机未验证**：`PHOTO_INTERVAL` + `lapse_time` 的合法性来自固件配置文件，**尚未在真机上跑过**。
      需实测三点：① 能否成功切到 `PHOTO_INTERVAL`；② `setValue(lapse_time)` 是否被接受（日志会打"间隔已设为 N s"）；
      ③ 达到间隔后相机是否真在连续出片。若失败，降级方案是手机侧跑定时器反复 `startCapture()`。
- [ ] Garmin FR255 与安卓的真机配对：首次需系统蓝牙配对后再 App 扫描连接。
- [ ] 真机 arm64 限制：x86 模拟器跑不了，必须真机。
- [ ] 手机同时 BLE(收心率)+WiFi(控相机) 的稳定性：本项目两无线分用，互不冲突。

## 7. 下一步（按优先级）

1. 电脑建 APK → 装真机。
2. FR255 开心率广播 + 手机试连，确认心率实时。
3. 手机连 GO Ultra 热点 → 填激活码激活 → 实测自动开/停。
4. 在 App 里把模式切到「间隔拍照」，用模拟心率验证 `lapse_time` 下发与连续出片（见第 6 节待验证项）。
5. （可选）若 `capture` 能在 BLE 下发，可改走 BLE 引导省去切热点。
