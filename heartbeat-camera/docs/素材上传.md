## 零、⚠️ 上传目标已切换（2026-09-23，v15）

**视频现在直投「白日梦想家（daydreamer）」服务，不再是本机/镜像上的调试服务。**

| 项 | 值 |
|---|---|
| 端点 | `POST https://your-server.example.com/api/jobs` |
| 请求体 | **视频原始字节**（raw body）—— **不是** `multipart/form-data` |
| `Content-Type` | 按扩展名判定，服务端只收 `mp4 / mov / webm / mkv / 3gp` |
| 鉴权 | `Authorization: Bearer <upload_token>` |
| 幂等 | `Idempotency-Key: <32 位 hex>`，**每段素材固定一个**，重试复用 |
| 上限 | 250MB（nginx `client_max_body_size 250m` 与 `MAX_UPLOAD` 一致） |
| 成功响应 | **HTTP 202** + job JSON（`id` / `state` / `message` / `player_url`） |
| 处理状态 | `uploading → queued → processing → ready`（失败停在 `failed`） |

地址与令牌存在 `AppSettings.DEFAULT_UPLOAD_URL` / `DEFAULT_UPLOAD_TOKEN`，换服务器改这两处即可。

### 契约是从服务端实现反查出来的，不是猜的

服务端在 `/opt/daydreamer/project/src/daydreamer_agent/web/server.py`，前端参考实现在 `/opt/daydreamer/web/upload.js`。两个关键点：

1. **`same_origin()` 只拦浏览器**：它检查 `Sec-Fetch-Site: cross-site` 与 `Origin` 头 —— App 发的裸请求两样都没有，直接放行，不需要伪造 Origin。
2. **上传令牌是受限凭据，权限被刻意做小了**：

   ```python
   if upload_access:
       # The phone's uploader is independent of its browser session. It
       # may submit a recording and check a known job, but cannot bind
       # a browser, list the library, fetch videos or restart paid work.
       if path == "/api/jobs" and self.command == "POST":   return self.upload()
       if re.fullmatch("/api/jobs/" + ID, path) and GET:    ...   # 查指定任务
       raise APIError(403, "上传凭据仅可上传视频及查询已知任务。")
   ```

   → **`GET /api/jobs`（列全部）会 403**。要列全量得用浏览器「连接码」换 session cookie，
   那是更大的权限，不该塞进手机端。所以 App 的做法是：上传成功时记下返回的 `job_id`
   （存 `AppSettings.uploadedJobIds`），「③」逐个 `GET /api/jobs/{id}` 查进度。

### 实测记录（2026-09-23）

```bash
TK=WB3P-0KlSPcQclH9R1I-XSpJCfQ8YVjdOgiUCOb9GGs
```

## 一、这个按钮到底做了什么

点一下，依次做 5 件事（每一步都会写进 App 日志区，也同步到 logcat 的 `HeartbeatUI`）：

```
① 若相机正在拍 → 先停（列素材前必须让相机把文件写完）
② 列相机素材   → 挑出最新的一条 .lrv
       └ 一个 .lrv 都没有时，兜底挑最新的一条 .mp4，并在日志里明说
③ 下载到手机缓存
④ .lrv → .mp4（remux 换壳，不重新编码）
⑤ 以「视频原始字节 + Bearer 令牌 + 幂等键」POST 到「素材上传」里填的服务器地址
```

对应代码：

| 步骤 | 文件 |
|---|---|
| ①②③ | `camera/CameraController.kt` 的 `listCameraMediaFiles()` / `downloadCameraMedia()` |
| ④ | `upload/LrvToMp4Converter.kt` |
| ⑤ | `upload/MediaUploader.kt` |
| 全流程编排 | `upload/ClipUploadManager.kt` |

## 二、四个关键设计决策（以及为什么）

### 1. 用 `sdk-camera` 自带的 `CameraDevice.file`，**不引 `sdk-media`**

列文件 / 下文件这两个能力，`sdk-camera` 自己就有：

```
CameraDevice.file  (= CameraFile)
  ├─ listMediaFiles(MediaFileType, includeRecording)          suspend → Result<List<String>>
  ├─ listMediaFiles(MediaFileType, offset, count, inclRec)    suspend → Result<Pair<List<String>, Int>>
  ├─ getFileInfoList()                                        suspend → Result<List<FileInfo>>
  └─ downloadMediaFile(remotePath, destPath, onProgress)      suspend → Result<String>
```

（签名是从 `verticalCamera-release.aar` 的 `classes.jar` 用 `javap` 反查出来的，实测确认。）

而 `sdk-media` 会传递引入 `bmgmedia` → `libarvbmg.so`(135MB) + `libarffmpeg.so`(13MB)，
**APK 会从 ~35MB 膨胀到 ~235MB**，为了「下一段视频」不值得。
（官方 demo 里的相册走的是 sdk-media 的 `WorkManager.getAllCameraWorks()`，
所以这几个低层接口 demo 没演示过 —— 这正是下面第 4 点要做多重兜底的原因。）

### 2. LRV → MP4 是**换壳（remux）**，不是转码

Insta360 的 `.lrv` 是**给手机端做快速预览的低码率副本**，本身已经是
H.264/H.265 + AAC 的 ISO-BMFF 流，只是扩展名不是 `.mp4`。
所以转换用 `MediaExtractor` + `MediaMuxer` 把音视频轨原样搬进新 MP4 容器：
**秒级完成、画质零损失、不吃 CPU**。

> ⚠️ 一句话提醒：**LRV 的画质明显低于相机里的主视频**。用它是因为**体量小、传得快**，
> 适合先把「拍完自动上云」这条链路跑通。
> 要原画质就改传主文件（固件里通常叫 `VID_*.mp4` 或 `.insv`）——
> 代码里已经有「没有 .lrv 就退到 .mp4」的分支，改成优先主文件只是换个筛选条件。

万一固件写的 LRV 头不规范（Extractor 读不出来），会自动退到
**「字节复制 + 改扩展名」**，日志会写明用了哪条路，**不会因为转换失败卡死整条链路**。

### 3. ⚠️ 上传必须**挑对网络出口**（这是最容易踩的坑）

真实场景是：手机为了控制相机 / 下素材，**必须连在 GO Ultra 的 WiFi 热点上**，
而那个热点**没有公网出口**。此时直接用默认网络发 HTTP，请求会打到相机热点上，必然超时
—— 这就是「连着相机就没法上传」的根因。

`MediaUploader.pickUploadNetwork()` 的处理：

| 当前网络情况 | 行为 |
|---|---|
| 默认网络**已通过联网验证**（普通家里/公司 WiFi） | 直接用默认网络，不绑定（服务器在局域网里也走它） |
| 默认网络**没有联网验证**（说明正卡在相机热点上） | 显式挑一个带 `NET_CAPABILITY_VALIDATED` 的网络（**优先蜂窝**），用 `Network.openConnection()` 把 socket 绑上去 |
| 地址是回环 `127.0.0.1` | 用默认网络（给 `adb reverse` 调试通道用） |
| 找不到任何已验证网络 | 用默认网络，并在日志里明说「可能没插卡/没开流量，大概率失败」 |

**效果：手机可以一边连着相机热点，一边用 4G/5G 把视频传上服务器。**

### 4. 「断点续办」：下载成功但上传失败，不用重下

手机连着相机热点时没公网，而下载又**必须**在相机热点下做 ——
所以「下载成功、上传失败」是完全正常的一种结果。

处理方式：上传失败时**故意把已转好的 mp4 留在缓存里**，
用户再按一次同一个按钮，程序检测到缓存里有文件就**跳过下载和转换，只重试上传**。
（否则每次失败都要从相机重拖几十 MB。）

## 三·补、两个必踩的隧道坑（v12 实测踩穿）

这两条会让「明明连上了却传不出数据」，而且**现象极其误导**，单独记一下。

### 坑 1：服务只监听 IPv4 → 手机侧收到 **0 字节**

`adb reverse tcp:8000 tcp:8000` 在**宿主机侧**是往 `localhost:8000` 建连的，
而 Windows 上 `localhost` 常常优先解析到 **IPv6 的 `::1`**。
如果服务只监听 `127.0.0.1`（IPv4），就会出现：

- 手机端 `nc`/浏览器**显示连上了**（TCP 三次握手成功，`netstat` 里能看到 `TIME_WAIT`）；
- 但**一个字节都收不到**，请求永远等不到响应。

自测方法（在这台电脑上）：

```bash
python -c "import socket;[print(a, (lambda s: (s.settimeout(2), s.connect((a,8000)), 'OK')[2])(socket.socket(f))) for a,f in (('127.0.0.1',socket.AF_INET),('::1',socket.AF_INET6))]"
```

若 `::1` 那条超时，就是这个坑。

**修法**：`upload_server.py` 已支持 `--host ::`（默认值），内核里关掉 `IPV6_V6ONLY` 走双栈，
于是 `127.0.0.1` / `::1` / 局域网 IPv4 三种访问方式同时可用。

### 坑 2：adb 守护进程被回收 → 转发凭空消失

如果 adb 服务是被某条命令**临时拉起来**的，那条命令一结束它可能就被回收，
于是 `adb reverse --list` 变空、转发失效。表现为「刚才还好的，现在怎么都不通」。

**修法**：让 adb 服务常驻（前台跑在一个不结束的终端里）：

```bash
D:\AndroidSdk\platform-tools\adb.exe -L tcp:5037 nodaemon server
```

**最快的端到端验证**（确认隧道真的通了，不必等 App 上传）：

```bash
# 让手机浏览器去请求电脑上的服务，然后看服务端日志有没有打出这一行
D:\AndroidSdk\platform-tools\adb.exe shell "am start -a android.intent.action.VIEW -d 'http://127.0.0.1:8000/health'"
```

服务端应打印：

```
[15:46:24] ← GET /health（来自 ::ffff:127.0.0.1:58902）
```

（`upload_server.py` 现在会记录**每一次** GET/POST 及来源地址，就是为了一眼看穿这类问题。）

> ⚠️ 别用 `toybox nc` 当客户端做这个测试：`nc 127.0.0.1 8000 < req.txt`
> 实测**连得上但对端收到 0 字节**（toybox 的 nc 在此用法下不写 stdin），
> 会让人误判成「隧道坏了」。用浏览器或 App 本身去验。

### 4.1 当前在用的服务器（阿里云 ECS）

| 部署脚本 | `deploy/ecs_setup.sh`，执行：`python deploy/remote_exec.py --file deploy/ecs_setup.sh` |

**隔离原则（重要）**：这台服务器上还有队友在跑 VS Code Server / Qoder，所以本服务

- 只占 `8000` 一个端口；
- 只用 `/opt/heartbeat-upload/` 与 `/var/log/heartbeat-upload.log` 两处路径；
- **不装任何 pip 包**（纯 Python 标准库）、不改系统 Python、不动别人任何配置。

实测部署后队友的进程（node×4 / Qoder / code-server）与其端口全部无影响。

> 安全组需要放行 **8000/TCP**（当前已放行）。如果哪天突然连不上，先查安全组。

### 4.2 协议

App 侧**只需要改「素材上传」里的地址**，上传协议就一个 `POST`：

```
POST http://<服务器地址>:<端口>/upload
Content-Type: multipart/form-data; boundary=...

file         <filename.mp4>   video/mp4        ← 视频本体
source       heartbeat-camera                  ← 固定标识，便于多端区分
clip         LRV_20260923_141530_00_001.mp4    ← 原始文件名（含拍摄时间）
sizeBytes    12345678
clientTime   2026-09-23 14:15:30
```

服务端返回 2xx 即算成功，响应体会原样打到 App 日志里（最长 512 字符）。
要集成到别的产品里，把 `upload_server.py` 的 `handle_upload()` 换成你的业务逻辑即可。

**几件上线前要注意的事：**

- **HTTP 明文**：本工程为了演示方便在 manifest 里开了 `android:usesCleartextTraffic="true"`。
  正式部署请换 **HTTPS**，并关掉这项（改用 `networkSecurityConfig` 白名单）。
- **鉴权**：当前没有任何鉴权。公网部署前请加 Token / 签名，否则等于开放了一个匿名文件上传口。
- **备案**：国内地域用域名对外提供 Web 服务需要 ICP 备案；不备案只能用 IP + 非 80/443 端口。
- **Nginx 上传限制**：默认 `client_max_body_size` 只有 1MB，要调大（`client_max_body_size 512m;`）。

### 4.4 ⚠️ 坑：`"%s:%s" % self.client_address` 会让**每一笔上传都空响应**

这是 **v13「上传失败」的真正根因**，单独记一条。

`--host ::` 走的是 **IPv6 双栈**，此时 socket `accept()` 返回的是
**四元组** `(host, port, flowinfo, scope_id)`（4 个元素，不是 2 个）。而

```python
peer = "%s:%s" % self.client_address     # ← 四元组 → 参数多于占位符
```

抛 `TypeError: not all arguments converted during string formatting`。
这一行**位于读取请求体之前**，于是请求体一字节没读、连接直接被关掉，
手机端 okhttp 只能看到：

```
❌ 上传失败：unexpected end of stream on com.android.okhttp.Address@...
```

（curl 端是 `(52) Empty reply from server`。）

**为什么只有 POST 挂、GET 一直正常**：`do_GET` 用的是带切片的 `_sock_name()`
（内部取 `client_address[:2]`），所以毫发无伤 —— 这也是它极具迷惑性的原因。

**修法**（已改）：

1. POST 里也改用 `self._sock_name()`；
2. 把 `do_POST` 整体包一层 `try/except`，任何未预期异常都回 **500 + traceback**，
   而不是让连接静默断开。
3. 同时把 `protocol_version` 设为 `HTTP/1.1`，让大文件上传的
   `Expect: 100-continue` 能正常协商（HTTP/1.0 下 `BaseHTTPRequestHandler`
   会跳过 100 处理）。

> 教训：**HTTP 处理器里任何异常都不能让它逃逸到 socket 层**，
> 否则客户端拿到的错误信息与真实原因毫无关系（「流意外结束」≠「服务端代码崩了」），
> 排查成本极高。

## 五、⚠️ 需要在真机上确认的两件事

这部分是**目前唯一的不确定点**，所以代码里做了多重兜底 + 全量日志：

1. **`listMediaFiles()` 返回的路径格式**。
   官方 demo 没演示过这个低层接口，不同固件的返回可能是
   `/DCIM/Camera01/LRV_xxx.lrv`、`LRV_xxx.lrv` 或其它形式。
   - 代码里对 **4 种 `MediaFileType` 取并集**（VIDEO / VIDEO_AND_PHOTO / MP4 / PHOTO），
     全空还会再试一次「翻页重载」版本；
   - 每种的条数、去重后的总条数都打日志：`📂 相机素材：VIDEO=3｜…（共 3 条）`；
   - 挑中哪一条也会打出来。**如果列表为空或不对，把这几行日志发出来即可定位。**

2. **当前固件是否真的落 `.lrv`**（本机实测连的是 **GO 3S**；GO Ultra 与 GO 3S 用同一套 SDK，无需分别处理）。
   如果素材里根本没有 `.lrv`，程序会**明确告诉你**并退到最新 `.mp4`，不会静默失败。

## 六、失败时的日志对照表

| 你看到的日志 | 含义 | 怎么办 |
|---|---|---|
| `❌ 相机未连接。…（下载素材必须走 WiFi）` | 没连相机 | 先连相机 WiFi 热点 → 点「连接相机」 |
| `📂 相机素材：…（共 0 条）` | 列文件返回空 | 先录一段；若已录过，把这条明细发出来（可能固件格式不同） |
| `⚠ 相机素材里没有 .lrv…退回上传最新的一段 MP4` | 固件不落 LRV | 正常兜底。要原画质可改传主文件 |
| `❌ 下载失败：…` | 相机 WiFi 断了 / 中途切走 | 保持连着相机热点重试 |
| `✅ 已输出 MP4（复制换扩展名…）` | LRV 头不规范，走了复制兜底 | 一般仍可播放；若不能播说明这段 LRV 需要专门处理 |
| `❌ 上传失败：…` 且日志里出口写「未找到可用公网出口」 | 手机没插卡/没开流量 | **先断开相机 WiFi**（文件已缓存在手机里），再点一次按钮即续传 |
| `🎉 上传成功（HTTP 200，出口：蜂窝数据…）` | 通了 | — |

## 七、上传结果查看（App「③」/ 浏览器网页）

上传成功与否，不用再靠猜。三条路都能看：

### 7.1 App 里：点「③ 查看已上传任务」

**这个按钮会按上传地址自动分两条路走**（`ClipUploadManager.refreshServerList()` 里按 URL 分流）：

| 上传地址形如 | 走哪条路 | 显示什么 |
| --- | --- | --- |
| `…/api/jobs`（daydreamer，**当前默认**） | 逐条 `GET …/api/jobs/{id}` | 本机上传过的任务状态（待处理/处理中/已完成…） |
| 其它（如本地调试服务的 `:8000/upload`） | `GET <根>/list` | 服务器上的文件清单（按日期文件夹分组） |

**为什么 daydreamer 只能逐条查**：上传令牌是受限凭据，`GET /api/jobs`（列全部）会返回 403
（服务端注释明说不能让上传方浏览整个素材库）。所以 App 在上传成功时把返回的 job id 记在
`AppSettings.uploadedJobIds`（逗号分隔，最多 40 条），之后按 id 逐条查。

走 **本地调试服务** 时显示的是清单（**只读，不碰相机、不影响上传**）：

```
共 3 个文件 · 23.15 MB
服务器目录：/opt/heartbeat-upload/videos
📁 2026-09-23（3 个文件）
　· LRV_20260923_160523_01_093.mp4 · 7.18 MB · 2026-09-23 16:47:29
　· VID_20260923_160523_00_093.mp4 · 8.00 MB · 2026-09-23 16:47:29
　· LRV_20260923_002605_01_092.mp4 · 7.97 MB · 2026-09-23 16:12:03
```

分组行 / 汇总行 / 任务行会加粗，和下面的明细行区分开。

### 7.2 浏览器：打开 `http://your-server.example.com:8000/`

服务器自带一个素材页，按文件夹分组列出全部视频，每条都能**直接播放**（可拖动进度）
和**下载**。演示、给队友看结果、确认某条视频是否真的传上去了，都很方便。

### 7.3 服务器上直接看文件

```bash
ls -lh /opt/heartbeat-upload/videos/2026-09-23/
tail -f /var/log/heartbeat-upload.log      # 每笔上传都会打印来源地址
```

## 八、后续可以怎么扩展

- **拍完自动上传**：现在是手动按钮。若要自动化，把 `ClipUploadManager.start()` 挂到
  `CameraController.Listener.onCaptureFinished` 上即可（注意：必须等相机把文件写完，
  代码里已有 `STOP_SETTLE_MS` 的等待逻辑）。
- **批量上传**：现在只传「最新一段」。`listCameraMediaFiles()` 已经把全量列表拿到了，
  循环下载即可。
- **只传主文件（原画）**：见第二节第 2 点的说明，改筛选条件即可。
- **断点续传**：现在是「整段重传」，若视频较大可改用 `Content-Range` 分片。
- **上传队列 + 失败重试**：目前失败后需要手动再点一次。
